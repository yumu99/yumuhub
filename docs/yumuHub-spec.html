yumuHub Spec
Technical Specification

A pocket gateway to many minds.

A personal, cross-device app that talks to any AI provider — Claude, OpenAI, and more — and runs a roster of genuinely independent agents, each carrying its own API key, personality, tools, and memory. Agents can message each other through a real bus, so delegating a big task to one never freezes the rest. Inspired by NanoClaw's "small enough to understand" ethos: extensible first, provider-agnostic, local-first, and simple to live with.

Extensibility ◆ P1 Multi-provider ◆ P2 Local-first ◆ P3 Simplicity ◆ P4
01

Overview & Goals

yumuHub is a single-user system for orchestrating multiple AI agents across Windows and macOS (with a clear path to mobile). Each agent is a self-contained configuration — model provider, its own API key, system prompt, enabled tools, and isolated memory — running as its own independent runtime. The app is the conductor; the agents are real, separate players that can also pass notes to each other.

Priorities — as you ranked them
1
ExtensibilityPlugins, tools & integrations are first-class. The system is a thin core + a wide plugin surface.
2
Multi-provider flexibilitySwap models per-agent in one tap. No provider lock-in; a normalized adapter layer.
3
Privacy / local-firstKeys, chats & memory live on-device by default. Sync is opt-in & end-to-end encrypted.
4
SimplicitySensible defaults so it "just works," without sacrificing the three goals above.
In Scope

Multi-agent chat · independent agent runtimes · inter-agent messaging · per-agent keys · provider switching · plugin tools · cross-device sync · local memory.

Out of Scope (v1)

Multi-user / team accounts · fully autonomous open-ended swarms · model fine-tuning · marketplace billing. Local models: supported but low-priority polish.

Success looks like

Hand Agent A a huge task; Agents B and C stay fully responsive and can even ask A for results — across Windows and your M1/M5 Macs.

02

Design Principles

Thin core, wide edges

The kernel only routes messages, manages keys, and loads plugins. Everything else — providers, tools, UI panels — is a plugin. New capability = new plugin, never a core rewrite.

Provider-agnostic by contract

Every model sits behind one ProviderAdapter interface. The app never speaks a vendor's raw API directly; adapters translate to/from a single internal message format.

The device is the source of truth

Data is born local and encrypted. The optional sync server is a dumb encrypted blob store — it can never read your content or keys.

Independence per agent

Borrowing NanoClaw's container ethos: each agent runs its own loop with sandboxed keys, memory, and tool permissions. A long task on one agent never blocks another — no shared-context bottleneck.

Config is data, not code

Agents, providers, and tool grants are declarative records you can export, version, and re-import. Reproducible setups, easy backups.

Graceful, observable failure

Rate limits, dead keys, and timeouts surface clearly with retry/fallback, never silent hangs. Every request is traceable.

03

Platform Targets

One codebase, native feel on each OS. Tauri 2 is the recommended shell: it uses each OS's native webview (WebView2 on Windows, WebKit on macOS), ships tiny binaries, and shares a Rust core across targets — with a ready path to iOS/Android later without a rewrite.

Windows 10 · AtlasOS

x64 build via WebView2. AtlasOS is a debloated Win10 — fine for Tauri, just ensure the Edge WebView2 runtime is present (bundle the evergreen installer, since AtlasOS may strip it).

macOS · M1 & M5

Both are Apple Silicon (arm64), so a single Apple-Silicon build covers M1 and M5 — no separate M5 work. Optionally ship a universal binary if you ever add Intel Macs.

Later · Mobile

Tauri 2 extends the same project to iOS/Android. Not in v1 scope, but the architecture won't fight you when you get there.

Build matrix note

Cross-compiling to macOS requires a Mac to sign & package; Windows builds are easiest on Windows or CI. A simple CI matrix (one macOS runner, one Windows runner) produces both artifacts on every release tag.

04

System Architecture

A local-first client on each device holds the UI, a pool of independent agent runtimes, a message bus, and an encrypted vault. A small sync relay (self-hostable) moves encrypted blobs between devices. Providers are reached directly from the device — the relay never touches model traffic or plaintext.

Key insight: model traffic flows device → provider directly using the agent's own key. The relay only ever sees encrypted blobs, preserving the local-first/privacy goal even when syncing.

05

Core Components

Six components, deliberately small. The kernel is tiny; capability lives in plugins and adapters.

01Orchestrator (Kernel)▸

Routes a user message to the active agent, assembles context (history + memory + tool defs), invokes the right provider adapter, and streams the response back. Handles tool-call loops, retries, and fallback chains.

Responsibility: message lifecycle, no business logic. ~ a few hundred lines, "small enough to understand."
event-drivenstreamingtool-loop
02Agent Runtime▸

Instantiates each agent as its own independent worker — separate execution context, message queue, and tool-loop. Binds the agent's key, system prompt, model, memory scope, and granted tools. Because each runs on its own loop, a long-running task on one agent never blocks the others.

This is the direct fix for the single-orchestrator bottleneck: agents are real, concurrent workers — not personas a single model role-plays in one shared context.
own worker/loopconcurrentscoped memorynon-blocking
03Message Bus▸

An in-process pub/sub + addressed-message router that lets agents and the UI talk to each other asynchronously. Agent A can send a request to Agent B and either await a reply or fire-and-forget; B processes it on its own loop and answers when ready.

Decoupling via the bus is what keeps the system responsive: messages queue per-recipient, so a busy agent backs up its own queue, not everyone's.
pub/subper-agent inboxasync req/reply
04Plugin Host▸

Discovers, validates, and loads plugins (tools, provider adapters, UI panels). Exposes a stable plugin API and a manifest/permission contract. This is the primary extensibility surface — your #1 priority.

A plugin declares: name, type, permissions, input/output schema, and a handler. The host wires it into agents that opt in.
manifestcapability tokenshot-load
05Provider Adapters▸

One adapter per provider, all conforming to a single interface. Translate the internal message format to vendor requests and normalize responses, tool-calls, token usage, and errors back.

Adding a provider never touches the kernel — it's just another plugin implementing ProviderAdapter.
ClaudeOpenAIOpenRouterOllama (local)
06Vault & Store▸

Vault holds API keys and secrets, encrypted with a device key in the OS keystore. Store holds conversations, agent configs, and per-agent memory in a local encrypted DB.

Keys never leave the device unencrypted and never pass through the sync relay in plaintext.
OS keystoreSQLCipherper-agent scope
07Sync Engine▸

Optional. Encrypts state client-side, pushes/pulls deltas via the relay, and merges with CRDTs so edits from two devices reconcile without conflict. Disable it entirely to stay fully local.

The relay is a "dumb" encrypted blob store — zero-knowledge by design.
E2E encryptedCRDT mergeself-hostable
06

Agents & Per-Key Model

An agent is a declarative record. Multiple agents can run side-by-side, each with its own provider and key, so you can isolate spend, limits, and personas cleanly.

// agent config record — exportable JSON
{
  "id": "agt_research",
  "name": "Research Buddy",
  "provider": "anthropic",
  "model": "claude-opus-4-7",
  "keyRef": "vault://keys/anthropic_personal",  // indirection, never the raw key
  "systemPrompt": "You are a meticulous research assistant…",
  "memoryScope": "agt_research",                // isolated
  "tools": ["web_search", "file_read", "calc", "send_to_agent", "spawn_agent"],
  "parentId": null,                        // set on spawned children
  "budget": { "maxChildren": 8 },        // children inherit, minus spawn_agent
  "params": { "temperature": 0.4, "maxTokens": 4096 },
  "fallback": { "provider": "openai", "model": "gpt-5", "keyRef": "vault://keys/openai_personal" }
}
Per-agent key

Each agent references one key by handle. Track spend & rate limits per agent; revoke one without touching others.

Isolation

Memory & tool grants are scoped to the agent id. No cross-agent leakage of context or secrets.

Fallback chain

If the primary key/model fails, the orchestrator retries the declared fallback automatically.

07

Inter-Agent Messaging

The problem this solves

In the swarm setups you tried, there was effectively one model role-playing several "agents" inside a single shared context. Give one persona a big task and the whole conversation stalls, because there was never more than one worker. yumuHub makes each agent a real, separate worker that communicates over a bus — so concurrency is genuine, not simulated.

Each agent owns an inbox. Sending a message to another agent is just dropping an envelope on the bus addressed to its id. The recipient handles it on its own loop and replies when ready. The sender chooses the mode:

Ask & await

Sender pauses its own turn for a reply (with timeout). Others keep running. Good for "B, summarize this file for me."

Fire & forget

Hand off a task and move on. The reply (or failure) arrives later as a new inbox message. Good for long jobs.

Broadcast

Post to a topic many agents subscribe to — e.g. "research findings" — for loose coordination.

Delegation is exposed to the model as an ordinary tool (e.g. send_to_agent), so an agent can decide to consult another mid-reasoning. Any agent can also spawn a sub-agent on the fly via spawn_agent — covered in 7.1 — to fan out a task and gather results.

// envelope on the bus — addressed, async, traceable
{
  "id": "msg_8f3a",
  "from": "agt_research",
  "to": "agt_writer",        // or "topic:findings" for broadcast
  "mode": "ask",               // ask | notify | broadcast
  "replyTo": "msg_8f3a",       // correlates the response
  "deadlineMs": 120000,
  "body": { "task": "Draft an intro from these notes…" }
}

A is mid-task and still delegates to B; C is untouched and fully available. No shared context means no global stall.

7.1 · Sub-Agent Spawning

A top-level agent may create a child agent at runtime via the spawn_agent tool. The child is a full independent worker (own loop, inbox, key, memory scope) — not a persona. Spawning is single-level: children are structurally barred from spawning, so the tree is at most one layer deep.

Spawn

Parent calls spawn_agent with a config (inline or by template id). Returns a childId the parent can message like any peer.

Inherit, minus spawn

Child clones the parent's provider, key, and tools — but the host strips spawn_agent from every child's grant set. A child cannot spawn, by capability, not just by budget.

Lifecycle

Ephemeral by default: child is reaped when its task resolves or the parent dies (cascade). Can be marked persist:true to outlive the turn.

Spawned agents register on the same bus, so a parent fans out work and collects replies through normal ask/notify/broadcast. Because children lack the spawn capability, fan-out stops at one level — no grandchildren.

// spawn_agent tool call — child is a real worker, scoped by the parent
{
  "tool": "spawn_agent",
  "args": {
    "from": "agt_research",            // parent (sets lineage)
    "template": "summarizer",         // or inline "config": {...}
    "overrides": {
      "model": "claude-haiku-4-5-20251001",  // cheaper child for grunt work
      "tools": ["file_read"]          // subset of parent's grants; spawn_agent always stripped
    },
    "persist": false,                  // reaped when task resolves
    "budget": { "maxChildren": 8, "maxTokens": 200000 }  // no depth: children can't spawn
  }
}
Guardrails — runaway prevention

Children never receive the spawn_agent grant, so recursion is impossible by design — the tree is capped at one level. Each spawn still carries a budget: max live children per parent and an aggregate token/cost ceiling. Hitting a limit fails the spawn_agent call (surfaced to the parent) rather than silently forking. A global live-agent cap and a kill-tree action backstop the whole hub.

Flat fan-out: each child is an independent worker, but none can spawn further. Budgets cap children-per-parent and total spend; killing the parent reaps its children.

// the single contract every provider implements
interface ProviderAdapter {
  id: string;
  listModels(): Promise<Model[]>;
  send(req: InternalRequest, key: SecretRef): AsyncStream<InternalChunk>;
  normalizeError(e: unknown): NormalizedError;
}
Why this serves Priority #2

Swapping a model is a one-field change on the agent record (provider + model + keyRef). No code path in the kernel changes — that's true multi-provider flexibility.

09

Plugin / Tool System

Your top priority. Tools, providers, and even UI panels are plugins sharing one manifest + permission model. A plugin is granted to specific agents — never global by default.

// plugin manifest
{
  "name": "web_search",
  "type": "tool",                 // tool | provider | panel
  "version": "1.2.0",
  "permissions": ["net:https"],   // capability tokens, user-approved
  "schema": {
    "input":  { "query": "string", "limit": "number?" },
    "output": { "results": "Result[]" }
  },
  "entry": "./handler.js"
}

Capability-scoped

Each plugin declares the permissions it needs (net, fs:read, clipboard…). You approve once; the host enforces at runtime.

Per-agent grants

Adding web_search to Agent A doesn't expose it to Agent B. Tool surfaces stay isolated.

Typed I/O

Schemas double as the tool definitions sent to the model and as validation guards on results.

Hot-loadable

Drop in a plugin and enable it without rebuilding the app — extensibility without redeploy.

Local encrypted DB is the source of truth. Sync is an opt-in CRDT layer over a zero-knowledge relay.

Sync flow

Encrypt locally → push deltas to relay → other devices pull & CRDT-merge → decrypt locally. The relay stores opaque ciphertext; it cannot read content, even in a breach.

12

Security & Privacy Model

Keys by reference

The UI and configs never hold raw secrets — only vault:// handles. The vault dereferences just-in-time at send.

Encryption at rest

DB via SQLCipher; secrets in the OS keystore (Keychain on macOS / DPAPI on Windows). Master key never persisted in plaintext.

Zero-knowledge sync

End-to-end encryption with per-device keys. The relay sees ciphertext + metadata only.

Plugin sandboxing

Capability tokens gate what a plugin may touch. Network/file access is explicit and per-grant — NanoClaw-style isolation.

Direct provider calls

Model traffic goes device→provider; no middleman server logs your prompts.

Bounded spawning

Children inherit a narrowed permission set with spawn_agent always stripped — so spawning is single-level by design. Per-spawn budgets, a global live-agent cap, and a kill-tree action backstop it.

13

Suggested Tech Stack

Picks that favor one shared codebase across Windows + macOS, strong local-first tooling, and a clean plugin boundary. Swap freely — these are starting points.

App shell

Tauri 2 + React or Svelte. Native webview per OS (WebView2 on Win10/AtlasOS, WebKit on macOS), tiny binaries, Rust core. Same project later targets iOS/Android.

Core / runtime

Rust for the kernel, agent workers & message bus (real concurrency via async tasks/threads), with a TypeScript plugin SDK. Streaming via SSE/WebSocket.

Agent workers & bus

Each agent = an async task with its own channel (e.g. Tokio + mpsc) — genuine non-blocking concurrency, not one shared loop.

Local store

SQLite + SQLCipher; Automerge / Yjs for CRDT sync; OS keystore (Keychain / DPAPI) for secrets.

Sync relay

Tiny Hono / Fastify (or Rust Axum) blob service. Self-hostable in one container.

Provider SDKs

Official Anthropic & OpenAI SDKs behind adapters; OpenRouter for breadth; Ollama for local models (low-priority, slots in as another adapter).

Why Rust for the core here

Your top need — many agents that don't block each other — is fundamentally a concurrency problem. Rust's async model gives each agent a real, cheap worker, and Tauri already uses Rust, so the core and the shell share one language across both OSes.
